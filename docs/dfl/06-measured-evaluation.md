# 6. Measured downstream evaluation

> **Evidence status: MEASURED, on generated tasks.** Every outcome below is the score of a real model
> call (Fireworks, through the SDK's own OpenAI-compatible adapter) on the context the SDK's store,
> journal, episode graph and projector assembled for the retention set under test, checked against
> ground truth by a deterministic verifier. The tool-call histories are generated by
> `dfl_bench.live.scenarios`, not recorded from production agent runs, and the answering turn has no
> tools. Read §6.8 before quoting any number.

## 6.1 What was measured

For each task the SDK replays a tool-call history (reads, a failed call, derived actions with
prerequisite edges, shaped exactly as `BaseAgent` records them), applies a retention set with
`InMemoryEpisodeStore.retain_only`, projects the context with `ContextProjector` and calls the model with a
three-part question about earlier results. Each answer is a value that sits in the full result of specific
episodes (the generator proves, for every task, that it is present in the model-visible context when
those episodes are retained and absent from the 160-character stub when they are compacted). A task's
score is the fraction of three answers that match exactly: 0, 1/3, 2/3 or 1. Three task families:
**ledger** (account owner, error code of a failed rate refresh, reconciliation total or snapshot),
**deploy** (replica count, failed health-check code, promoted artifact digest) and **triage**
(ticket queue, failed runbook-search code, assignee or on-call pager). Budgets are 40-60% of the
history's tokens, never below 1.15 times the cheapest set that holds every answer, so a perfect score is
always attainable.

Methods compared, all at the same budget: static PCKP (the SDK default), greedy PASK, random feasible,
linear Ranking-DFL + PCKP, MLP Ranking-DFL + PCKP, set-level regression + PCKP, and top-k with
feasibility repair. All learned methods are trained, per world, on measured outcomes of candidate
retention sets for training tasks only (six candidate generators, three trials each, two on-policy rounds,
preferences kept only when significant).

The design, hypotheses, test, and the measurement-validity gate were fixed in
`benchmarks/dfl/PREREGISTRATION_LIVE.md` before the primary run. Its SHA-256 is in the results file; it was
not committed first, so the hash shows only which text was used.

## 6.2 Runs and provenance

| Run | What | Status |
|---|---|---|
| Probes and pilots | Model and reasoning-effort probes (seeds 777, 900), end-to-end pilot (seed 9000, 1,393 calls) | Disclosed; used only to choose the model (`glm-5p3-flash`), `max_tokens` 16384 and `reasoning_effort` low, and to find defects |
| **Primary** | Five independent worlds (seeds 4000-4004), 108 tasks each; 60 / 15 / 25% train / validation / test split by template; 24 test tasks per world, **120 pooled from 20 distinct templates** | **Pre-registered** |
| Held-out family | Train and validate on two families, test on the third; seeds 4100-4102; 36 test tasks each | Pre-registered secondary |
| Utility floor | The primary worlds and rotations re-run with `QuantizationPolicy(floor=1)` | **Exploratory**, proposed after seeing the rotations |
| Cross-model | The primary retention decisions re-scored by `deepseek-v4p1-flash`, no retraining | **Exploratory**, added after the primary result |

**Deviations before any method comparison was read** (all listed in the pre-registration): the first
launch hit provider rate limits (HTTP 429) and a first backoff design stalled; `reasoning_effort` low was
adopted after a probe showed identical accuracy and 7-10x fewer output tokens; and a split rule that glued
tasks by dependency topology collapsed each world into one group (0 validation, 5-10 test tasks), so it
was replaced by template, exact question and identical-history identity, and the design was widened to five
worlds. Only split sizes and the validity controls were read from the degenerate run. The earlier outcomes
were reused as cache where task, selection, trial and settings matched; the ledger file name carries a digest of model and parameters so
outcomes under different settings can never mix.

**Spend.** About 52,000 recorded model calls in total, 134 million provider-reported input tokens and
6.4 million output tokens, plus a few hundred unrecorded probe calls. I do not know the account's price per
token and report tokens only.

## 6.3 Measurement validity (pre-registered gate)

Gate: with every fact-bearing episode retained the mean score must be at least 0.90; with every
fact-bearing episode removed, at most 0.10. **Result: 1.000 and 0.000 on all 120 primary test tasks and
on all 108 rotation test tasks.** Format failures (truncated, filtered or unparseable replies, scored 0):
32 of 16,289 primary calls (0.2%), 52 of 17,488 rotation calls (0.3%); the gate threshold was 3%. The
whole primary pipeline was re-run from its cache and reproduced every method's mean score to three
decimals, so retention decisions are deterministic.

## 6.4 Primary result (pre-registered)

Mean task score on 120 test tasks (95% interval over tasks), and the paired difference against static
PCKP with a template-clustered 95% interval (20 clusters). Full tables: `results/live/live_tables.md`.

| Method | Mean score | All 3 answers right | Failure-critical recall | Difference vs static | Holm p (6 comparisons) |
|---|---|---|---|---|---|
| static-pckp | 0.756 [0.710, 0.804] | 0.469 | 0.842 | - | - |
| greedy-pask | 0.748 | 0.461 | 0.808 | -0.008 [-0.019, +0.003] | 0.18 |
| random-feasible | 0.546 | 0.119 | 0.500 | -0.210 [-0.294, -0.124] | 0.003 |
| **linear-dfl** | 0.868 [0.834, 0.897] | 0.636 | 0.975 | **+0.111 [+0.040, +0.190]** | 0.003 |
| **mlp-dfl** | 0.903 [0.872, 0.930] | 0.725 | 0.967 | **+0.146 [+0.080, +0.222]** | 0.003 |
| regression-pckp | 0.905 [0.877, 0.932] | 0.722 | 1.000 | +0.148 [+0.083, +0.221] | 0.003 |
| topk-repair | 0.862 | 0.628 | 0.975 | +0.106 [+0.039, +0.178] | 0.003 |

**H1 (linear > static) is supported; H2 (MLP > static) is supported** (the pre-registered family of two,
Holm-adjusted clustered p = 0.001 for both, the smallest value 4,000 resamples can give; the column above
corrects over all six comparisons instead). Every method used 86-90% of the budget; the learned
methods do not win by spending more. All 480 primary static, linear, MLP and regression selections
were `optimal` with gap 0.

**What the result does and does not say about Ranking-DFL specifically.** Among learned methods
(Holm over four pairs): linear Ranking-DFL scores **below** both the MLP (-0.035 [-0.057, -0.016], Holm
0.002) and set-level regression + PCKP (-0.037 [-0.060, -0.017], Holm 0.002); the MLP is indistinguishable
from regression (-0.002, Holm 1.0). So the supported claim is that *learning objective coefficients from
measured set-level outcomes beats the static weights*; a simple regression on the same data does as well
as the best ranking model, so nothing here shows the pairwise ranking loss to be the better way to learn
them. A plausible reason, which I did not test, is data: only about 115-135 significant training preference
pairs survive per world (most candidate pairs tie), while regression uses every candidate's mean outcome.

**By task family (primary, pooled; exploratory breakdown, `results/live/by_family.md`).**

| Family (test tasks) | static | linear | MLP | regression |
|---|---|---|---|---|
| ledger (36) | 0.448 | 0.762 (**+0.315**) | 0.815 (**+0.367**) | 0.802 (**+0.355**) |
| triage (60) | 0.844 | 0.911 (+0.067) | 0.922 (+0.078) | 0.933 (+0.089) |
| deploy (24) | **1.000** | 0.917 (**-0.083**) | 0.986 (-0.014) | 0.986 (-0.014) |

The gain is concentrated where static weights fit the task badly (ledger). Where static is already perfect
(deploy) learning cannot improve it and the linear model is measurably worse. The pooled mean therefore
depends on how many tasks of each family land in the test split.

## 6.5 Held-out family (pre-registered secondary; no pooling)

Train and validate on two families, test on the unseen third (36 tasks, one world each).
Difference vs static, template-clustered 95% interval; `results/live_heldout/live_tables.md`.

| Unseen family | static | linear | MLP | regression + PCKP |
|---|---|---|---|---|
| ledger | 0.460 | 0.515 (+0.056 [+0.015, +0.096]) | 0.426 (-0.034 [-0.086, +0.019]) | **0.802 (+0.343 [+0.293, +0.389])** |
| deploy | 1.000 | 1.000 (0.000) | 0.907 (-0.093 [-0.130, -0.046]) | 0.954 (-0.046 [-0.102, -0.009]) |
| triage | 0.815 | **0.454 (-0.361 [-0.426, -0.287])** | 0.759 (-0.056 [-0.130, +0.019]) | 0.889 (+0.074 [+0.028, +0.120]) |

**Generalisation to an unseen task family is not supported for the ranking-trained models.** The linear
model beats static only on ledger, ties it on deploy and is far worse on triage; the MLP never beats
static. Only set-level regression is consistently at or above static (and large on ledger).

The triage failure has a concrete mechanism. The linear model there kept only **36% of the token budget**
and covered **45%** of the needed evidence: with features unlike its training families it rated many
episodes at or below zero, the documented clipping turned those into zero utility, and the solver, which
prefers the cheaper of equal-utility selections, kept almost nothing. Static PCKP cannot fail this way
because its provenance and recency terms make every episode positive.

## 6.6 Exploratory: a positive utility floor

That mechanism suggested a minimal SDK change, `QuantizationPolicy(floor=...)` (default 0, so nothing
existing changes): every episode is worth at least `floor` quantized units, which breaks ties toward using
the budget. It was proposed after seeing §6.5, so it is exploratory, and it was evaluated on the same
tasks with `floor=1` (`results/live_floor/`; only 279 new model calls were needed). Changes versus static:

| | primary (120) | ledger | deploy | triage |
|---|---|---|---|---|
| linear, floor 0 -> 1 | +0.111 -> +0.119 | +0.056 -> +0.056 | 0.000 -> 0.000 | **-0.361 -> +0.028 (n.s.)** |
| MLP, floor 0 -> 1 | +0.146 -> +0.139 | -0.034 -> -0.034 | -0.093 -> -0.093 | -0.056 -> **+0.065 [+0.037, +0.093]** |

The floor repairs the budget under-use (triage budget use returns to 88%) without changing the primary
result, and leaves the other held-out conclusions as they were: ranking-trained models still do not beat
static on deploy, the MLP is still not better on ledger, and regression remains the most robust.

## 6.7 Exploratory: a second model

The same retention decisions (no retraining) were scored by `deepseek-v4p1-flash`
(`results/live_cross/cross_model.md`). Mean scores on the 120 test tasks, primary model / second model:
static 0.756 / 0.731, linear 0.868 / 0.842, MLP 0.903 / 0.889, regression 0.905 / 0.882, random
0.546 / 0.510. Differences against static under the second model: linear **+0.111 [+0.036, +0.197]**,
MLP **+0.158 [+0.090, +0.236]**, regression +0.152 [+0.078, +0.236]. The mean absolute per-task
disagreement between the two models is 0.03-0.06. The ordering and the size of the gains hold across the
two models. The second model produced more format failures (81 of 1,146 calls, 7%, scored 0), which lowers
its absolute scores.

## 6.8 What the evidence supports and does not

**Supported (measured):**

* On task families seen at training time (unseen templates), learning retention coefficients from measured
  outcomes and optimising them exactly improves real task success over the SDK's static weights:
  +0.11 to +0.15 mean score, success on all three answers 47% -> 64-73%, failure-critical recall 84% -> 97-100%.
  The result is stable across a second model.
* The retention decisions keep their solver certificates (`optimal`, gap 0) and are auditable; the gain is
  not bought with extra tokens.
* Learned coefficients can be harmful when the task family is unseen, and the budget-under-use failure is
  diagnosable and fixable by a floor.

**Not supported:**

* That the pairwise ranking loss is the right way to learn the coefficients: set-level regression on the
  same data is as good or better in every comparison, and linear Ranking-DFL is significantly worse than it.
* Generalisation of ranking-trained models to unseen task families.
* Any gain on tasks where the static weights are already near perfect (deploy).

## 6.9 Limitations and remaining work

* **Generated histories, one task style.** Histories are generated by me, not recorded from production
  agents; every task is a three-part lookup over earlier tool results. Real agent memories may have different
  structure. The generator was validated, not calibrated against real traffic.
* **No tools in the answering turn.** A real agent could fetch a compacted result through its journal
  handle; here a compacted fact is simply lost. Retention therefore matters more than it would in a full
  agent loop.
* **Two models, one provider.** One primary model and one cross-check; reasoning effort `low`.
* **Small samples.** 120 pooled test tasks from 20 templates in the primary comparison; 36 tasks per
  rotation. Preference data are sparse (about 115-135 significant training pairs per world).
* **Static is untuned.** The static baseline uses the SDK's default weights; a domain-tuned static policy
  was not tested and might close part of the gap. It is the most important missing baseline.
* **Exploratory analyses are exploratory.** The family breakdown, the floor and the cross-model check
  were not pre-registered; their intervals are not corrected for the number of looks.
* **The pre-registration has no external timestamp** (§6.1).
* **Remaining work:** a domain-tuned static baseline; recorded real agent histories; a version of the
  answering turn with journal access; more families and a sweep over budget tightness; and richer preference
  construction for the ranking models (the data-sparsity hypothesis above).

## 6.10 Reproducing

```bash
cd benchmarks/dfl
PYTHONPATH=../../src:. python -m dfl_bench.live --out results/live                       # primary
PYTHONPATH=../../src:. python -m dfl_bench.live --seeds --heldout-families ledger deploy triage \
    --heldout-seed 4100 --out results/live_heldout                                       # rotations
PYTHONPATH=../../src:. python -m dfl_bench.live --quantization-floor 1 \
    --heldout-families ledger deploy triage --out results/live_floor                      # exploratory
PYTHONPATH=../../src:. python -m dfl_bench.live --cross-models accounts/fireworks/models/deepseek-v4p1-flash \
    --out results/live_cross                                                              # exploratory
PYTHONPATH=../../src:. python -m dfl_bench.live.breakdown results/live/live_results.json
```

These need `FIREWORKS_API_KEY` and make paid calls. Every call is appended to
`results/<run>/outcomes-<digest>.jsonl` first, so a repeat run is served from the ledger. Raw ledgers and
`live_results.json` are git-ignored (large); the Markdown tables are tracked. Tests: `tests/dfl_bench/`
(`-m live` runs the five tests that call the real model; they skip without a key).
