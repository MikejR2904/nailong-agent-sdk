# `state/` - durable run state: plans, the typed graph, the controller and project state

Everything that must survive a restart and be explainable afterwards. There are four independent state machines, each with its own store: (1) the **plan** (`planning.py`) is validated deterministically; (2) the **graph run** (`graph.py` + `harness_coordinator.py` + `run_state_store.py`) schedules approved plan tasks in waves and is the only carrier of lateral data between agents; (3) the **controller** (`orchestration.py` + `controller_runtime.py`) owns plan approval, dispatch, bounded repair and escalation; (4) the **project state** (`project_state_*.py`) is the bounded working memory a `BaseAgent` reads every turn. Persisted records are integrity-hashed: run and controller records use a snapshot plus an append-only sidecar whose prefix hash the snapshot names, and project state uses one hash-chained event file per revision. The stores still assume **one writer at a time per run root** for record contents: the harness coordinator and the project-state store detect that another writer changed a file and refresh or refuse instead of overwriting it, but two writers saving at the same instant can still interleave. Several hazards are closed: ids (`run-N`, `controller-N`, `orchestration-N`) are reserved atomically across processes through exclusive claim files, every caller-supplied id is validated before it becomes a path, approvals are persisted per run, and one project-state store instance is safe across threads.

**Algorithms & invariants.** Every stage failure - the explicit `record_stage_failure`, a failed graph execution, and a rejected provenance check - goes through `_record_stage_failure`, so each one emits `controller.stage-failure` and records the repair-attempt and escalation metrics. Each transition (plan, approval, dispatch, stage failure, completion, cancellation) runs inside `_transaction` together with its save; `cancel` checks `require_cancellable` before it touches the graph run, and a graph-run write (discovery, shared value, node result, lateral dependency) is refused once the controller is completed or cancelled. Every command that takes a controller id holds the controller's cross-process lock from the reload of the machine to the end of the command (the run and project-state locks nest inside it), so two processes driving one controller take turns; a command that reads a project state and applies a transition derived from it holds the project's lock for both. `execute_graph` holds no lock while the executors run and takes the controller's lock again to record the outcome. A command that writes several stores (a node result into the run and then into project state; a cancel into the run, then project state, then the controller) can fail between two writes. Each store stays consistent and the cached machine is rolled back, and the graph run is the authority for the rest: project state holds one work item for each terminal run result (`record_node_result`, `execute_graph` and `cancel` all write them) and a cancelled run means a cancelled controller. `reconcile` restores both from the run and is safe to repeat; `tests/state/test_multi_store_atomicity.py` fails each write of each such command in turn and checks the outcome against the fault-free one.

Each run also carries ceilings (the orchestrator sets them from `OrchestrationPolicy`; they default to the hard limits): a plan cannot declare caps above them and no capacity grant can pass them, so a batch that would pass a ceiling is refused with `ELASTIC_NODE_CEILING_REACHED` or `ELASTIC_DEPTH_CEILING_REACHED` instead of being deferred. A child may depend only on what its requester can already see and may only narrow the requester's routing references, so a spawn can never widen what a node reads. Refusals are typed and recorded; only a cap that a grant could raise defers.

### `state/graph.py` - deterministic wave scheduler and authoritative typed run state

*1463 lines · depends on: `foundations/dependency_graph.py`, `foundations/identifiers.py`, `state/elastic.py`, `state/graph_models.py`, `state/shared_state.py` · used by: `state/harness_coordinator.py` · re-exported at the package root: 1 name(s)*

**Role in the workflow.** One `StateGraph` per run. The coordinator asks for the runnable wave, marks it RUNNING, persists, runs host executors concurrently (at most 32 per wave unless told otherwise), then commits terminal results in sorted node-id order. Lateral discoveries and values are published only after their producer has completed and are routed by exact reference to consumers that have not started. Hard dependencies must complete: a failed, blocked or cancelled one blocks its dependents, and a node blocked by its own result (for example a pending approval) can be re-opened with `reopen_blocked`, which also re-opens the dependents that were blocked only because of it. **Elastic continuation.** A completed result may carry `spawn_requests`; `mark_terminal` judges them in order and, for the accepted batch, creates the exploration children (`elastic:<parent>:<id>`, one level deeper), one join (`join:<parent>`) that depends on the parent and waits for every child, and puts the parent's not-yet-started dependents behind the join, all in the same commit as the result and recorded in `spawn_records`. Fan-in edges are soft: a failed child lets the join run with its typed failure, while a blocked or cancelled child blocks it. Joins count against `max_elastic_nodes` with the children, so a batch of N requests costs N + 1. A batch over the plan's depth or node cap is deferred as a whole behind a join that is blocked by its own result until `grant_elastic_capacity` (up to the run's ceilings) or `decline_elastic_requests` decides it; a batch over a ceiling is refused request by request, because no grant could admit it. While a wave runs, each node's context carries an `ElasticReservation` on a per-wave ledger, so tasks that run at the same time see each other's queued requests; the commit stays the authority. After a crash, `recover_interrupted` returns an interrupted node to PENDING only when the caller names it or a replay policy accepts it, and fails every other one.

**Algorithms & invariants.** Each cursor keeps the sidecar's committed byte length and a running SHA-256, so a save appends and hashes only the new entries instead of re-reading the file; the cursor is rebuilt once from the verified prefix after a restart. A sidecar shorter than its committed length raises (it was truncated outside the store). `locked` serialises the writers of one run across processes and `save` takes it itself, so even a bare save is safe; `HarnessCoordinator` holds it across a whole read-modify-write. The version check inside the lock catches the writer that read the run earlier and saves without having held the lock throughout (`execute_run` between its waves) instead of letting it truncate the sidecar suffix another process committed. Readers take no lock: the snapshot names the sidecar prefix it owns, so a reader sees one complete generation. A save still rewrites the whole fixed-state snapshot (nodes, edges, statuses, results) and hashes the whole run, so the cost of a save grows with the size of the run and the total with its square. `execute_run` saves once per wave and `StateGraph.snapshot` reuses its item dumps, which cut a 400-node dependency chain from about 10 s to about 4 s (about 7 s for 600 and 17 s for 1,000 nodes on the development machine); two fsyncs per save and the snapshot bytes are what remains.
