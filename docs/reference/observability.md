# `observability/` - tamper-evident records of what a run did

Three independent records of a run, all written outside the model's context: the **telemetry ledger** (SQLite, one hash chain per run, plus metric observations), the **audit transcript** (append-only JSONL per run, hash chained, fsynced per entry, with a readable markdown rendering) and the **profiler** (timed spans for harness phases). `BaseAgent` writes all three; the MCP tools and `developer_tools/inspect.py` read and verify them. Every durable payload is passed through the secret redactor and rejects hidden-reasoning keys before it is hashed.

**Algorithms & invariants.** Each entry hashes its own canonical JSON with `integrity_hash` blank and stores the previous entry's hash, so editing, deleting or reordering any entry breaks verification of everything after it. Per-entry `fsync` makes entries durable but is synchronous work done on whichever thread calls `append`. A transcript file belongs to exactly one run id (`file_safe_name` is injective); an entry of another run raises `AUDIT_TRANSCRIPT_RUN_MISMATCH`, and an unreadable last line raises `AUDIT_TRANSCRIPT_CORRUPT` instead of being skipped. Reads are streamed and stop at the requested boundary or limit.

*400 lines · depends on: `observability/telemetry_models.py` · used by: `observability/metrics.py` · re-exported at the package root: 1 name(s)*

**Role in the workflow.** `register_standard_metric_definitions` loads this table into the telemetry store at the start of every run so each recorded observation has a formula, unit, aggregation rule and missing-data rule that `create_run_report` can apply.

**Contents**

- `_definition(metric_id: str, name: str, unit: str, direction: str, formula: str, **kwargs: Any) -> MetricDefinition` - Small factory that builds a `MetricDefinition` from positional id/name/unit/direction/formula plus keyword fields, and fills `instrument` from `_instrument_for` unless one is given. · *Called by:* `observability/metric_definitions.py::<module>`

**Algorithms & invariants.** `STANDARD_METRIC_DEFINITIONS` is a tuple of definitions grouped by prefix: `agent.*` (model-turn, rejection, tool, verification and escalation counts, wall/CPU duration), `context.*` (estimated input tokens, working budget, deadlocks, PASK and exact-PCKP compaction counts and certificates), `controller.*` (repair attempts, escalations), `model.*` (provider-reported token usage; explicitly unavailable until an adapter reports it, never estimated), `retrieval.*` and `tool.*`. No domain-specific metric is built in: a host registers its own definitions with `register_metric_definition` and records observations against them. Each definition also declares an `instrument` kind derived from its unit and aggregation: 22 counters, 10 gauges and 3 histograms. No standard metric uses `up_down_counter`; the kind is available to a host's own definitions.

**Algorithms & invariants.** Nothing here imports OpenTelemetry: the formats are the W3C Trace Context ones, so the `trace_id`, `span_id` and `parent_span_id` of `TelemetryContext`, `AgentRunProfile` and the `agent.profile-completed` payload can be passed to an OTLP exporter unchanged. A trace id is 32 lowercase hex characters and a span id 16, neither all zeros; `TelemetryContext` refuses anything else, naming the field. Measured on the development machine, `new_span_id` takes about 0.2 microseconds, `format_traceparent` about 0.9 and `parse_traceparent` about 1.8; a run formats one header per model turn and per tool call, and builds the process resource once. The SDK records every run, so the header it sends is always sampled (`01`), whatever flags arrived on the one that started the run; the incoming flag is parsed and reported, not propagated. `tracestate` is neither read nor sent.
