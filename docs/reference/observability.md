# `observability/` - tamper-evident records of what a run did

Three independent records of a run, all written outside the model's context: the **telemetry ledger** (SQLite, one hash chain per run, plus metric observations), the **audit transcript** (append-only JSONL per run, hash chained, fsynced per entry, with a readable markdown rendering) and the **profiler** (timed spans for harness phases). `BaseAgent` writes all three; the MCP tools and `developer_tools/inspect.py` read and verify them. Every durable payload is passed through the secret redactor and rejects hidden-reasoning keys before it is hashed. Runs carry W3C trace and span ids (`trace_context.py`), and `otlp.py` exports a run's spans, log records and metrics to an OTLP/HTTP collector by reading the ledger, never on the write path. The writers all honour the per-run fence that retention raises before it deletes a run (`foundations/run_fence.py`), and the telemetry file can be compacted with an explicit `vacuum`.

**Algorithms & invariants.** Each entry hashes its own canonical JSON with `integrity_hash` blank and stores the previous entry's hash, so editing, deleting or reordering any entry breaks verification of everything after it. Per-entry `fsync` makes entries durable but is synchronous work done on whichever thread calls `append`. A transcript file belongs to exactly one run id (`file_safe_name` is injective); an entry of another run raises `AUDIT_TRANSCRIPT_RUN_MISMATCH`, and an unreadable last line raises `AUDIT_TRANSCRIPT_CORRUPT` instead of being skipped. Reads are streamed and stop at the requested boundary or limit. A run that retention is pruning is fenced: `append` waits for the fence to lift and re-checks it inside its transaction, and `quiesce` lets retention drain an append that was already in flight, so the footprint it records is the last one.

**Algorithms & invariants.** `STANDARD_METRIC_DEFINITIONS` is a tuple of definitions grouped by prefix: `agent.*` (model-turn, rejection, tool, verification and escalation counts, wall/CPU duration), `context.*` (estimated input tokens, working budget, deadlocks, PASK and exact-PCKP compaction counts and certificates), `controller.*` (repair attempts, escalations), `model.*` (provider-reported token usage; explicitly unavailable until an adapter reports it, never estimated), `retrieval.*` and `tool.*`. **Algorithms & invariants.** Spans come from the `agent.profile-completed` event of each run: the most recent 512 spans it kept, so `spans_omitted` reports what a very long run lost. Ids are the hex strings the profile already holds (OTLP JSON encodes ids as hex, not base64), nanosecond times and 64-bit counts are decimal strings, enums are integers, field names are lowerCamelCase. The bodies were checked by parsing them with the official `opentelemetry-proto` classes. A graph run is exported as one `invoke_workflow` span (from the controller's events) that parents the root span of every node's agent run; dependencies between nodes are in the run record and, when the caller passes them, become span links between the nodes' root spans (`nailong.link.basis` = `declared-graph-edge`), which state what the graph declared and not that one span caused the other. Metrics are sent as delta data points because the catalogue's `sum` aggregation adds observations to a run total. The exporter has no queue and no background thread: it is a function over the ledger, so nothing is lost when the process exits and nothing runs inside an agent.

**Algorithms & invariants.** A checkpoint is as independent as the place it is kept: someone who can rewrite the run root and the checkpoint store together, or who holds the key, can produce agreeing records, and one who can delete the newest checkpoints leaves an older, shorter one. The store is therefore kept on another volume or host and the key is not stored in the run root. A run that grew since its newest checkpoint is `advanced`, not a failure. The telemetry head is read from the event JSON, not the denormalized hash column. One export or verification scans each chain twice (its chain check, then one pass for the head and the wanted hash); a re-export used to scan each chain five times. A tombstone retires a checkpoint only when its final heads equal that checkpoint's exactly; a tombstone that is longer than the checkpoint says only that the run was not cut short before it was pruned, and the events between are gone. The `terminal-link` entry is its own audit record so that a small `max_payload_chars` cannot truncate it away.

**Algorithms & invariants.** Nothing here imports OpenTelemetry: the formats are the W3C Trace Context ones, so the `trace_id`, `span_id` and `parent_span_id` of `TelemetryContext`, `AgentRunProfile` and the `agent.profile-completed` payload can be passed to an OTLP exporter unchanged. A trace id is 32 lowercase hex characters and a span id 16, neither all zeros; `TelemetryContext` refuses anything else, naming the field. Measured on the development machine, `new_span_id` takes about 0.2 microseconds, `format_traceparent` about 0.9 and `parse_traceparent` about 1.8; a run formats one header per model turn and per tool call, and builds the process resource once. The SDK records every run, so the header it sends is always sampled (`01`), whatever flags arrived on the one that started the run; the incoming flag is parsed and reported, not propagated. `tracestate` is neither read nor sent. Derived ids make a run's trace survive a crash, a resume and another process with nothing persisted: executing the same run again continues the same trace. Only the graph-run trace and span are derived; every agent run's own root span id is random, so a node that runs twice after a crash appears as two spans in the trace, never as a duplicate id.
