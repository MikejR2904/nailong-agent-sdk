# `developer_tools/` - read-only maintainer utilities and the `nailong-agent-sdk-dev` command

Five deterministic helpers behind one CLI: generate the public API catalogue from `__all__`, validate a JSON or YAML contract file, verify and summarise a run's evidence chains without writing anything, cross-check a project's recorded tool-result hashes against the result journal, and run the closed Ruff quality check. None of them runs a model or a tool. The CLI prints JSON and exits 0 on success, 1 when a verdict field of the result (`valid`, `passed`, `telemetry_chain_valid`, `audit_chain_valid`, `verified`) is false, 2 for a command-line usage error and 3 when the input could not be read or the check could not run (a one-line message on stderr, no traceback).

### `developer_tools/attribute_defect.py` - which write of an artifact introduced a defect, and which agent made it

*286 lines · depends on: `foundations/contracts.py`, `foundations/suffix_search.py`, `tools/artifacts.py` · used by: `developer_tools/__init__.py`, `developer_tools/cli.py` · not re-exported at the package root*

**Role in the workflow.** Answers 'which agent introduced this defect into this file?' for an artifact written through `ArtifactStore`. `attribute_defect(run_root, relative_path, is_defective)` reads the ordered write history of the path, evaluates the caller's check on the content of as few versions as it needs (`find_suffix_start`: the newest, then 1, 2, 4, ... back, then bisection) and names the first defective version of the unbroken defective suffix, the writer recorded with it (agent identity, agent run, role, node, task, run, tool, call id, iteration), the last clean version and the writers who wrote afterwards. `content_check` builds the four checks the command line offers. Pass the directory the artifacts were written under (a task workspace, or the run root of a graph run), not its parent.

### `developer_tools/attribute_failure.py` - which failure, and which model decision, stopped a run

*390 lines · depends on: `developer_tools/decision_links.py`, `developer_tools/diagnose.py`, `foundations/contracts.py`, `observability/audit_log.py`, `state/graph.py` · used by: `developer_tools/__init__.py`, `developer_tools/cli.py` · not re-exported at the package root*

**Role in the workflow.** Answers 'what is responsible for this run stopping?' from the ledgers, read-only. For a graph run, `attribute_graph` applies the structural model the scheduler uses (a node runs only when every hard dependency completed; a failed fan-in parent does not block) and computes, for each node that stopped for its own reason, `responsibility` (1 for its own stop plus, for every node it holds up, 1 divided by the number of independent failures holding that node), `released_alone` (the nodes that would run if only it were repaired), `also_requires` (the other roots that must be repaired for the rest of what it holds) and, for any blocked node, its independent causes and one blocking path. `attribute_failure(run_root, run_id)` adds the model decision behind the failure: for an agent run the turn that issued the failing call, produced the rejected output or reported itself blocked (`decision_links.py`), for a graph run the same for each of the ten most responsible roots whose agent run is in the ledgers. `nailong-agent-sdk-dev attribute-failure [--node ID]` prints the model and exits 1 when `ok` is false.

**Algorithms & invariants.** Scope: this is structural attribution over the declared dependency model, not statistical causal inference. The scheduler's rules are the structural equations, a repair is an exact intervention (`StateGraph.released_by`, checked against re-executing 120 random graphs with the repaired nodes completed) and `responsibility` is its Shapley value (checked by enumerating every coalition on 120 random graphs), which equals the Chockler-Halpern degree of responsibility for a node that fails if any of its causes fails. It says nothing about why a model chose an action and does not replay a run with a different decision. Invariant: the responsibilities add up to the number of roots plus the number of dependency-blocked nodes, each blocked node being shared out whole between its causes. A node held up by two failures is in neither's `released_alone` and in both `also_requires`. Roots are ranked by responsibility, then by when they stopped, then by id. Cost is linear in nodes plus edges plus the size of the root sets: about 0.12 s for 5,000 nodes with 4,700 blocked and 100 roots, 30 ms for 2,000 nodes with 3,600 explicit edges. Bounded: 50 roots, 50 blocked nodes, 100 released and 50 co-required nodes per root, 20 path nodes and ten roots linked to decisions, each with the count left out.

### `developer_tools/attribute_lineage.py` - trace a failing run back through what it read to the write or the retrieval that began it

*644 lines · depends on: `developer_tools/attribute_defect.py`, `developer_tools/decision_links.py`, `foundations/contracts.py`, `foundations/hashing.py`, `foundations/text.py`, `memory/context_projection.py`, `observability/audit_log.py`, `tools/artifacts.py` · used by: no other module (entry point or re-exported only) · not re-exported at the package root*

**Role in the workflow.** The other attribution tools say where a failure became visible: a rejected result, a stopped node, one named path. This one follows data. From the journal of a run it recovers what the run retrieved, asks two caller-supplied checks which retrievals are defective, and follows the first defective one: an artifact version to its writer and then to that writer's own retrievals; a stored result fetched again with `get_tool_result` to the run that recorded it; a command output, a fetched page or a search to the call that retrieved it, where the trace ends because that data comes from outside the SDK's records. It ends the same way at a write whose run read nothing defective (the defect began in that run's own decision), at identical content written twice (reported as ambiguous), at a writer with no run id and at `max_depth`.

**Algorithms & invariants.** Everything reported is *observed* (it is in the journal: this run called this tool at this position and got this result) or *inferred* (a hint produced only on request). The relation between a retrieval and a later write of the same run is `precedes`, observed, with `causal=false`: the records show the order and not what the model used. With `infer_verbatim=True` a write whose text contains, as an exact match, a line of at least `min_verbatim_chars` characters of the retrieved text also gets a `verbatim-containment` relation, `inferred`, `causal=false`; a near-copy gets none. Nothing is concluded from similarity. A read is matched to artifact versions by artifact id (`read_artifact`, `grep_artifact`, `diff_declared_artifacts`) or, for `read_file`, by the versions of the path whose lines equal the window returned; it is defective only when every candidate version fails `is_defective`. A retrieval is a process output when the tool is `run_registered_command` or its result has the shape of a `ProcessExecutionRecord`. Data that reached the run by any other path (a shell command that wrote a file, `grep` or `glob` over the workspace) is not an input here, and a summary says so: "only the inputs the journal recorded were checked".

**Algorithms & invariants.** The link is a lookup: the iteration on the finding selects the audit entry and the call id on the finding (or the one call of the turn) selects the call. A terminal tool failure carries its call because the `terminated` event records the failure's bounded details (`tool`, `tool_call_id`); a run recorded before that has only the iteration, so a batch turn comes back `issued-the-batch` with every call id as a candidate. The audit transcript bounds each entry (8,192 characters by default); a longer turn is stored as a preview with its hash, so the arguments are unavailable and the reference says so. The code table is closed on purpose: a new failure code is `unlinked` until someone decides what it is about.

**Algorithms & invariants.** A finding is produced only for the event types in `_EXTRACTORS`; everything else is background. Errors are a failed terminal event, a rejected verification, a failed tool call, a graph execution that failed or blocked, a stage failure and a rejected provenance contract; warnings are a cancelled run, a blocked tool call, a rejected candidate output, a retried or cancelled model turn, a failed stream listener, a failed checkpoint and a cancelled controller. A recovered failure is still a finding: a run can be `completed` and `ok` with a `first_error` from an earlier iteration. The verdict comes from the graph record when there is one (failed, then cancelled, blocked, incomplete, completed) and from the terminal event otherwise; `ok` also needs both chains to verify and a terminal link that is not broken. The reason of a tool call that never ran (bad arguments, a hook denial) is in the ledger only because `tool-batch-completed` carries each failed outcome's code and a message of at most 300 characters; a call that ended the run before the batch completed (an undeclared tool, a missing executor, a timeout) is named by the `terminated` event's `failure_details`; a run recorded before that has the status and code alone. The nodes a root held up are the nodes whose root causes include it (`StateGraph.root_cause_sets`), not the nodes reachable from it, so a failed fan-in parent, which does not block, holds up nothing. Output is bounded: 50 findings, 50 roots, 100 listed descendants per root and 50 unfinished nodes, each with the count left out. Nothing is written: telemetry and audit open read-only, `RunStateStore(read_only=True)` creates no directory, and the only files a read can add are SQLite's own `-wal` and `-shm` side files, as `inspect_run` does. Cost is linear in the events and in the graph's nodes plus edges: about 0.2 s for a graph of 5,000 nodes with 4,700 blocked, where recomputing each blocked node's causes separately took 50 s.
