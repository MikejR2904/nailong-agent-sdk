# `agent/` - the BaseAgent turn loop, model adapters, verification and orchestration

`base_agent/` is the single-task runtime: one `BaseAgent.run` is a bounded loop of context projection, one model turn, and governed tool execution until the model returns an accepted final answer or the run is blocked, failed, cancelled or out of iterations. `model.py` defines the provider-neutral model contract; `openai_compatible/` implements it (plus embeddings and vision) over Chat Completions. `verification.py` holds named, host-registered output gates. `runtime.py` wires durable stores around an agent, `task_runner.py` runs one task from caller-supplied model, tool, permission and limit parameters (the MCP `run_agent_task` tool), `graph_agent_executor.py` runs agents as graph nodes, and `orchestrator/` compiles a user policy and an already-proposed plan into a controller-governed multi-agent graph. Model output is always treated as untrusted proposals.

### `agent/base_agent/agent.py` - the single-task agent loop

*2711 lines · depends on: `agent/base_agent/types.py`, `agent/model.py`, `agent/verification.py`, `foundations/contracts.py`, `foundations/detached.py`, `foundations/errors.py`, `foundations/hashing.py`, `memory/context.py`, `memory/context_projection.py`, `memory/episode_models.py`, `memory/episode_store.py`, `memory/episodes.py`, `observability/audit_log.py`, `observability/metrics.py`, `observability/profiler.py`, `observability/telemetry_models.py`, `observability/telemetry_store.py`, `observability/trace_context.py`, `state/project_state_engine.py`, `state/project_state_models.py`, `state/project_state_store.py`, `tools/tools.py` · used by: `agent/base_agent/__init__.py` · re-exported at the package root: 1 name(s)*

**Role in the workflow.** Per iteration: check the run deadline and cancellation; project context (compact episodes, select observations); project the bounded project state; enforce the three budget guards; call the model under a watchdog; validate the response as an `AgentTurn`; then act on it. A `blocked` turn ends BLOCKED; a `final` turn is validated and optionally gated; a tool turn runs a governed batch whose results become observations, episodes and project-state transitions. Every exit goes through `_terminate`, which records the agent result in project state, seals the profile, emits telemetry and audit entries, and builds the `AgentResult`. An instance runs one task (its profiler allows a single run). A cancellation token does more than stop the loop between iterations: it is raced against every awaited model call, tool call, hook and verification gate, so cancelling interrupts a call that is still running. With an episode store built around a `SemanticCompactor`, compacted episodes are archived, summarized and verified by the projection and the model receives their verified digests next to the stubs of the rest.

A blocking call run on a thread cannot be stopped from outside; the OpenAI-compatible adapter runs its request on a detached daemon thread (`foundations/detached.py`), so the run ends at once and the request finishes, or times out, on its own. A tool that is interrupted may already have had side effects. What cancelling a model request did is reported by the adapter, in three levels that are never conflated: the task was cancelled and nothing a late response carries can commit (always); the request was aborted by closing its connection (`HttpxAsyncJsonTransport` and the streaming transport) or left running on a detached thread until the provider answers or its timeout passes (the blocking transports); and the provider confirmed stopping the work (only a host-supplied provider cancellation can say so). ### `agent/periodic_checkpoints.py` - signed checkpoints and artifact anchors taken while a run is going

*102 lines · depends on: `agent/runtime.py`, `foundations/logging.py`, `observability/telemetry_models.py`, `tools/artifact_anchor.py`, `tools/artifacts.py` · used by: `agent/task_runner.py` · not re-exported at the package root*

**Role in the workflow.** A checkpoint taken once, when a run ends, leaves everything a crash interrupts uncovered. `PeriodicCheckpoints` runs a daemon thread that, every `interval_seconds`, exports a signed run-head checkpoint of the run and anchors its artifact write log, so a killed run keeps the records taken before it died: anything cut from before the newest of them is detected, and only what was written after it is not. `AgentTaskRunner` starts it when `TaskRunOptions.checkpoint_interval_seconds` is set (and refuses the option when the service has no checkpointer) and stops it when the agent returns, before the final checkpoint.

**Algorithms & invariants.** A failure of one checkpoint is counted, logged and recorded as `run.checkpoint-failed` with subject `periodic`, and never stops the run. Reading the chains while the run appends to them is safe: the telemetry store serializes access and the audit append is one locked write (a stress test takes more than five checkpoints while another thread appends for three seconds and finds no torn read).

**Algorithms & invariants.** A run is a telemetry run id (a task id): its events and metrics, its audit transcript and the journal files recorded under it. A run is pruned whole or not at all, because removing a prefix would break its hash chain. It qualifies when it has an `agent.terminated` event (or the policy says `include_unfinished`), its last event is older than `older_than_seconds`, it is not among the `keep_most_recent` newest, and both chains verify; a run with a broken chain is reported and left, as evidence. Nothing is deleted without a policy from the caller: no threshold is built in. Order matters for crashes: the tombstone is written first, then the journal, the audit files and the telemetry rows, so the run stays discoverable by its telemetry until the last step and a second pass finds the tombstone by run id, telemetry sequence and head hash and finishes the job without writing another. The tombstones form their own hash chain (`.agent-retention/tombstones.jsonl`), appended under `.agent-retention/retention.lock`, so editing or dropping one is detectable; a tombstone is the only record of a pruned run's final heads and tool-result hashes, which is what lets `verify-evidence` keep vouching for project-state evidence whose journal file is gone. A run that is revived between examination and deletion is caught by the telemetry sequence check under the store's write transaction (`TELEMETRY_RUN_CHANGED`); an event arriving after the last check but before the final delete is the one unguarded window, which is why `older_than_seconds` should be far longer than any task's resubmission delay. Journal handle numbers are never reused (`.high-water`). Not pruned: project states, graph runs, controllers, orchestrations, episode records, exported reports, workspaces and journal files recorded without a run id. The bytes a report counts are the logical size of what was removed. The audit and journal files are deleted outright; the telemetry database reuses the pages its deleted rows held, so it stops growing, but its file does not shrink until a `VACUUM`, which needs a quiet store and is left to the operator. Pruning is fenced: `_prune_one` raises the run's fence, waits for the writes already in progress by entering each store's critical section once, confirms the run received no new event, writes the tombstone, deletes, and releases the fence, so an event accepted before the fence is in the tombstone's footprint and one after it is refused with `RUN_PRUNING` (the writer may wait the fence out). A prune that dies is finished by running the same policy again. An anchor (`anchor_path`) is the independent record that makes removal of the newest tombstones detectable; without one the log proves only that nothing in the middle was changed.

**Algorithms & invariants.** Process-starting options (command templates, stdio MCP servers) are accepted only when the runner is created with `allow_process_options=True`; the MCP service sets that only when `AGENT_RUNTIME_ALLOW_PROCESS_OPTIONS=1`. Approvals are given in the request (`approved_capabilities`, recorded as `approval.decided` and attributed to `run-options` or to the `approved_by` the Python caller names) or, with `approval_mode` `wait`, while the run is paused; a capability that needs approval and does not have it ends the run BLOCKED naming the capability (or, after a rejection or a timeout, the approval). Each running task owns an `ApprovalRegistry` on its token, so approval ids repeat across tasks (`approval-1`) and every decision names its task. A wait is bounded twice: by `approval_timeout_seconds` and by the tool-call watchdog and run deadline, which `TaskRunOptions` refuses to set shorter. Cancelling a run that is waiting interrupts the wait (`RunCancelled`) and ends the run CANCELLED. Python hooks, verification gates and sub-agents stay a feature of the Python API (`AgentTaskRunner.run`): over MCP a caller has only the options `TaskRunOptions` names. Cancellation interrupts a model call, a tool call or an approval wait that is in flight.
