# Pre-registration: measured downstream evaluation of Ranking-DFL retention

Written 2026-10-22, before the primary run exists. Its SHA-256 is stored in the results file. It was
not committed before the run, so the hash only shows which text the analysis used.

## What is measured

Downstream performance is the score of a **real model call**, not a formula. For each task the SDK's
own machinery (episode store, tool-result journal, episode graph, context projector, `ModelContext`,
`OpenAICompatibleAgentModel`) assembles the context for a chosen retention set, the model answers a
three-part question about earlier tool calls, and a deterministic verifier compares each answer with
ground truth. A task's score is the fraction of the three answers that are exactly right
(0, 1/3, 2/3, 1). Retention matters because the answer values sit in the full result of particular
episodes: the generator verifies, for every task, that each value is present in the model-visible
context when its episode is retained and absent from the 160-character stub when it is compacted.

**What this is not.** The tool-call histories are generated by `dfl_bench.live.scenarios` (three
families: ledger reconciliation, deployment promotion, ticket triage), not recorded from production
agent runs. The answering turn has no tools, so it cannot recover a compacted result by fetching it,
as a real agent could. One model is used. Conclusions are about this task distribution and this model.

## Fixed design

* Model: `accounts/fireworks/models/glm-5p3-flash` on Fireworks through the SDK's OpenAI-compatible
  adapter; temperature 0.6, `max_tokens` 16384, `reasoning_effort` `low`, per-trial `seed` = trial index. This model and the
  token limit were chosen in disclosed pilots (§ Pilots) because it followed the output contract
  without failures, was fast, and scored 1.00 with all evidence retained and 0.00 with the evidence
  removed.
* Primary run: seeds 4000-4004 (five independent worlds). Per world: 3 families x 6 template
  variants x 6 instances = 108 tasks, split by template (60% / 15% / 25% train / validation / test;
  groups sharing a template, an exact question or an identical history never cross a split), 7-11 episodes per task, budget
  40-60% of the history's tokens (at least enough for the cheapest sufficient set).
* Training: six candidate generators as in the synthetic benchmark; 3 trials per candidate; two
  on-policy rounds; preference policy `alpha = 0.05`, effect at least 0.15, at least 2 trials;
  linear model (`l2` chosen on validation) and MLP (`hidden in {8, 16}`, `l2 in {1e-3, 1e-2}` chosen
  on validation); regression + PCKP and top-k with repair as baselines.
* Evaluation: on test tasks each method's selection is measured with 3 trials; the task score is the
  mean over trials. Held-out preference accuracy uses test candidates with 3 trials each.
* Token cap: 120 million input tokens. If it is reached, the run is reported as incomplete.

## Measurement-validity gate (decided before looking at any result)

On the test tasks, with every fact-bearing episode retained the mean score must be at least 0.90, and
with every fact-bearing episode removed it must be at most 0.10. If either fails, the measurement is
declared invalid and the primary hypotheses are reported as **inconclusive**, whatever they show.
Calls that end in a format failure (truncated, filtered, unparseable) score 0 and are counted; if they
exceed 3% of calls, that is reported prominently.

## Primary hypotheses

Mean measured task score on test tasks, paired by task, against static PCKP at matched budgets:

* H1: `linear-dfl` > static PCKP.
* H2: `mlp-dfl` > static PCKP.

Test: two-sided template-clustered bootstrap p-value of the mean paired difference (4,000 resamples,
seed 0), pooled across the five worlds; Holm correction over the two hypotheses; family-wise level
0.05. A hypothesis is *supported* iff its Holm-adjusted p < 0.05 and the difference is positive;
otherwise *not supported*.

## Secondary analyses (descriptive; no claim beyond the stated interval and correction)

* All other methods against static PCKP, template-clustered intervals, Holm over those comparisons.
* Learned methods against each other, Holm over 4 pairs.
* Held-out pairwise preference accuracy; evidence coverage; failure-critical recall (whether the episode
  holding the error code is retained); token use; solver status.
* Held-out-family rotations (seeds 4100-4102): train and validate on two families, test on the third,
  one rotation per family, 3 trials, run only after the primary run completes. Same tests, reported as
  a generalisation check, with the three rotations as separate groups and no pooling claim.
* Measured-outcome failure rate and the measurement-validity result.

## Pilots (disclosed; not part of the analysis)

* Model probe, 2026-10-22: 9 tasks (seed 900) x 6 models x 2 conditions (about 108 calls). First attempt
  used `max_tokens` 1024 and retained over-budget sets that the SDK's projector compacted again
  (a probe error, since fixed by making the executor refuse over-budget retention); second attempt used
  `max_tokens` 4096 and relaxed budgets. Those results chose the model and the token limit.
* Reasoning-effort probe, 2026-10-22 (seed 777, up to 90 tasks per condition, about 400 calls). With
  every fact retained, default and `low` effort both scored 1.00 on 90 tasks (median output 252 vs 35
  tokens); with every fact-bearing episode removed both scored 0.00 on 48 tasks (median output 1,141 vs
  102 tokens). Calls on answer-less contexts at default effort were slow and cost-dominating, so the
  primary run uses `low`. Outcomes recorded under any other setting are never reused: the ledger file
  name carries a digest of the model, provider and parameters.
* End-to-end pipeline pilot, seed 9000, 27 tasks (1,393 calls, 3.3M input and 1.2M output tokens), to
  find plumbing defects. It showed that 46 of 47 format failures were truncations at `max_tokens` 4096
  (reasoning ran past the limit), which score 0 for reasons unrelated to retention; the limit was raised
  to 16384 for the primary run. It also showed one call per second at concurrency 8, so the primary
  run was first launched at concurrency 24 (see Deviations). Its results are not used.

## Deviations

Any change after seeing primary results will be listed here with its reason, and the original analysis
will still be reported.

* 2026-10-22, before any method comparison had been looked at: the first complete launch ran seeds
  4000-4002 with a split rule that also glued together tasks sharing a dependency *topology*. Every
  family has a fixed shape, so that rule collapsed nearly all tasks into one group and left 0 validation
  and 5-10 test tasks per world. Only the split sizes and the validity controls (1.0 and 0.0) were read;
  no method comparison was. The split now groups by template, exact question text and identical
  history (`content`); topology shared across templates is a family property and is what the
  held-out-family rotations test. Because about a dozen test templates would make the clustered test
  weak, the design was also changed, before any comparison, to five worlds of 108 tasks (seeds
  4000-4004) and a 120 million-token cap. Ledger rows from that launch are reused where the task,
  selection, trial and settings match.
* 2026-10-22, before any primary result existed: the first launch (concurrency 24) stopped after 96
  recorded calls with HTTP 429 from the provider (a burst rate limit; it cleared within minutes). No
  result had been computed or examined. A second launch with a shared fixed cooldown reached only about 0.15 calls per second because all
  workers paused and resumed together, so it was stopped (no result computed). The executor now adapts
  its concurrency (halve on a rejection, regrow on success, up to 16) with a shared retry-after
  cooldown and jitter, and `max_attempts` is 12. The 96 recorded outcomes came from
  identical code, tasks and settings and are kept in the ledger as cache.
